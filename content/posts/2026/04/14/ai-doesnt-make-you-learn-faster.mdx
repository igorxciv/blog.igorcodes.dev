We like to say that AI helps us code faster, so it must help us learn faster. Sometimes that's true. But finishing a task and learning from it are different outcomes, and AI is very good at the first one. That sounds obvious when you say it slowly. It gets less obvious when a model hands you working code in ten seconds and your brain gets a tiny productivity cookie.

In a domain I already know, AI is a great accelerator. It writes the boilerplate and drafts the boring tests. In a domain I'm still learning, it can remove the exact friction that would have taught me something.

That's the uncomfortable part. AI changes which parts of the work I still do myself, and those parts decide what I learn.

<KeyPoints>

- You can finish a task with AI and learn almost nothing from it.
- In an Anthropic study, developers who used AI to learn a new library scored lower on a follow-up quiz and saved almost no time.
- Skill comes from guessing wrong and debugging your way out, and that's the first work people hand to the model.
- While you're learning, ask AI for concepts and critique, and keep the debugging for yourself.

</KeyPoints>

<Callout title="Context" type="note">

This post builds on Anthropic's research article [AI assistance and coding skill acquisition](https://www.anthropic.com/research/AI-assistance-coding-skills). I won't summarize the whole paper. I care about one practical question. What happens when AI helps you finish a task before you understand it?

</Callout>

## Anthropic's study found a gap in understanding

[Anthropic ran a randomized trial](https://www.anthropic.com/research/AI-assistance-coding-skills) with 52 mostly junior software engineers. All of them wrote Python every week, and none of them knew Trio, an async Python library. Each person built two features with Trio, some with an AI assistant and some without. Then everyone took a quiz on the concepts they had just used.

<VisualGrid columns="2">
  <VisualCard eyebrow="Quiz score" title="50% with AI, 67% without" tone="warning">
    The largest gap between the groups was on debugging questions, the skill you need most when code breaks.
  </VisualCard>
  <VisualCard eyebrow="Time saved" title="About two minutes">
    The AI group finished slightly faster, but the researchers found the difference wasn't statistically significant.
  </VisualCard>
</VisualGrid>

The lazy reading is "AI is bad for learning." I don't buy that, and the study doesn't claim it. My reading is narrower.

<PullQuote>

AI can help you produce an answer without helping you build the mental model behind it.

</PullQuote>

This was one study with one library and a 35-minute task, so I wouldn't stretch it over every learning situation. But the pattern will feel familiar to anyone who has used AI to pick up a new stack. You get something running and ship the change. Then the code breaks in a slightly different way, and you realize you never learned why it worked.

## The hidden cost is skipped practice

People who defend AI for learning usually talk about access, and access is real. A beginner can ask the questions they were too embarrassed to ask a coworker. You can get an explanation at 11 PM without waiting for anyone. But answers are only one piece of learning, and you build most engineering skill in the annoying middle.

<Compare title="Two ways through the same task">

<CompareColumn title="Doing it yourself">

1. A problem you can't solve yet
2. Make a guess
3. Write an imperfect version
4. Hit a confusing error
5. Debug the mismatch
6. Your mental model updates

</CompareColumn>

<CompareColumn title="Asking AI first" muted>

1. A problem you can't solve yet
2. Ask for the solution
3. Paste the answer
4. It works, so you move on
5. Mental model unchanged

</CompareColumn>

The left path is slow, and it's where the useful reps happen. You find out what the API expects. You learn which errors matter and which ones are noise. You learn what an abstraction hides, and what "async" means when your code behaves differently from the picture in your head.

So the real question is which friction AI removes. Skipping boilerplate is good, and skipping syntax lookups is usually fine. <mark>Skipping the part where you form a hypothesis, test it and find out why it failed is where the damage happens.</mark>

Say you're learning a new framework feature. You ask the model to implement it, and the code works. Nice. Now check whether you picked up any of this:

- which lines are required and which are style
- what assumptions the implementation makes
- how to debug it when the next case is slightly different
- when not to use this pattern

If you can't answer those, the model built a temporary bridge over the part you didn't understand. Next time you need to cross, the bridge won't be there. Sometimes that's the right trade. Deadlines exist, and production bugs don't care about your learning journey. When the goal is skill, though, you pay for those skipped reps later.

## Performance and learning can come apart

<mark>Performance means you finished the task, and learning means you can do more next time.</mark> The two often happen together, which is why people mix them up. A calculator improves your arithmetic performance without making you better at arithmetic. Google Maps gets you to the restaurant, and you still don't know the city.

AI works the same way. In a domain I understand, the downside is small, because I can smell weird code and reject a bad abstraction. In a domain where I have no judgment yet, I can easily mistake "the code runs" for "I understand the code."

Most arguments about AI and learning get messy because they blend these two rows. A senior engineer using AI in a familiar stack and a beginner using it to enter a new one are doing different things.

One is speeding up execution. The other may be outsourcing practice.

## Paste and pray feels like debugging

Asking AI for help is normal now. The workflow I worry about looks like this:

```text
run code -> see error -> ask AI -> paste fix -> run again -> see another error -> ask AI
```

It feels like debugging, and it usually skips the most important step. <mark>Real debugging starts with a hypothesis.</mark> You think something like this:

```text label="Hypothesis"
I think this fails because the value is undefined at this boundary.
```

Then you inspect the value. Maybe you're wrong. Good, now you update your model. In the paste-and-pray loop the model does that thinking, and you become the person who moves text between the editor and the chat window.

The study saw a version of this. Four participants leaned on AI to debug and verify their code. They averaged 24% on the quiz, the lowest of any group, and took about 31 minutes, the longest. The seven who asked only conceptual questions and fixed errors on their own averaged 65% in about 22 minutes. Those groups are tiny, and the authors say this part of the analysis doesn't prove cause and effect. It still matches what I'd expect.

I don't judge anyone for using this as a survival tactic. If production is down, fix it. Use the model, read the logs, ask a coworker, sacrifice a keyboard if needed. As a default way to learn, though, it's weak. You can fix today's error and still be stuck tomorrow when the same class of error shows up with different wording.

## The role AI plays decides what you keep

I don't think the answer is to avoid AI while learning. That's unrealistic, and it throws away a patient tutor. The better question is what job AI does in your learning loop.

<VisualGrid columns="2">
  <VisualCard eyebrow="Weak mode" title="Full delegation" tone="warning">
    "Write this for me" is efficient when you already know the pattern. It's risky when the pattern is the thing you need to learn.
  </VisualCard>
  <VisualCard eyebrow="Weak mode" title="Debug proxy" tone="warning">
    You send every error to the model and paste every fix. The task moves, and your debugging instinct gets no practice.
  </VisualCard>
  <VisualCard eyebrow="Stronger mode" title="Concept-first questions" tone="accent">
    Ask why the pattern works and where it breaks before you ask for any code.
  </VisualCard>
  <VisualCard eyebrow="Stronger mode" title="Generate, then take apart" tone="accent">
    Let the model write an example, then break it down and explain it back in your own words.
  </VisualCard>
</VisualGrid>

AI shows up in all four modes. What changes is who builds the mental model.

## How I use AI when I'm learning something new

When I pick up a new library or language feature, I put constraints on the tool. They aren't fun. Without them, though, the tool pulls me toward the fastest answer instead of one I understand.

### Write the first version yourself

Read the docs and write the awkward version. Let the error message punch you in the face a little. That friction gives you hooks, so when AI later explains a better approach, you have something to compare it with. Without that first attempt, even a clear explanation slides right off.

### Ask for concepts before code

Instead of starting with this:

```text label="Prompt"
Implement this for me.
```

try this:

```text label="Better prompt"
Explain the simplest version of this pattern.
What problem does it solve?
What assumptions does it make?
Where does it usually break?
Give me a small example, but don't optimize it yet.
```

That turns the model from a code vending machine into something closer to a tutor. Models can be confidently wrong, so still check what it tells you.

### Predict before you run

Before running generated code, decide what should happen. Before reading the model's explanation of a bug, guess the cause. If you never predict, you never test your own model, and testing it is most of what learning is.

### Rebuild the important part from memory

After AI gives you an implementation, close the chat and rebuild the core of it yourself. You don't need every line. You're checking whether the structure lives in your head or only in the chat transcript.

### Make the model question you

My favorite prompts flip the direction:

```text label="Prompts"
Here is my explanation of how this works. What am I missing?

Ask me three debugging questions about this code. Don't give me the answers yet.
```

You stay the one doing the work. The model becomes a sparring partner instead of a designated hitter.

## Teams will feel this in code review

This doesn't stay a personal problem. If junior engineers mostly use AI to produce answers, they can ship more code on weaker foundations. That looks fine for a while, because pull requests still appear and tickets still move.

Then review gets harder, because the author can't explain the trade-off. Incidents get scarier, because the generated code is production code now. AI often writes decent code. <mark>The cost shows up later, when the engineer doesn't know why the code is decent or how to change it safely.</mark>

So review has to change too. "Does it work?" and "Do the tests pass?" aren't enough anymore. I'd add questions like these:

- Can the author explain the trade-off?
- Do they know how it fails?
- Can they debug it without going straight back to the model?
- Can they tell when the model invented something?

Prompt fluency helps. The skill that matters here is judgment.

## Keep the parts of the loop that teach you

I don't treat AI as a miracle tutor or as poison for learning. It changes the environment you learn in. Good learning in that environment often feels slower than AI-assisted output, and sometimes that slowness is the work itself.

<Checklist title="In practice">

- Use AI freely for work you can already evaluate.
- Write the first attempt yourself, even if it's bad.
- Form your own guess about a bug before you ask the model.
- Treat working code as unproven understanding until you can rebuild it from memory.
- In review, ask the author to explain the trade-off, and judge the explanation along with the code.

</Checklist>

<Takeaway>

AI can make you faster at producing software. Whether it makes you a better engineer depends on which parts of the loop you keep. Give away the typing. Keep the guessing and the debugging until you can do them without help.

</Takeaway>
